# Messaging framework

**The messaging framework is the answer sheet to the buying committee.**

The Buying committee output names every buying role and the key question each one asks. This output writes the answers: one message per buying role, in buyers' words, resting on a proof point that exists. If the buying committee work has not been done, do it first, because a messaging framework without it collapses back into personas invented in a workshop.

## Two deliverables

**1. The messaging sheet.** The working framework as a plain spreadsheet or document on the client's own drive. Messaging hierarchy at the top, one row per buying role, the message, the proof point beside it. No analysis, no key finding, no drawing. It is built to be copied from on an ordinary Tuesday, to be read by the client's own AI tools, and to be the baseline Message drift later checks the live site against. This is what the client owns on the last day. In the app it also exports as an AI context file for ChatGPT, Claude or outbound tools.

**2. The report.** How the sheet gets judged and presented: proof point grades drawn, the two tests shown, the key finding, the limitations. The report is the showable artefact. The sheet is the usable one.

Nobody writing an email opens a styled report to copy a message. Ship both, and never let the report substitute for the sheet on a real engagement. For a demo or portfolio piece, the report alone is enough.

## Counts per buying motion, never added

Where the company sells through more than one buying motion (self-serve and purchased on behalf, say), those are **separate sales with separate counts, and the counts are never added together.** Three buying roles in one sale and five in the other means nobody ever faces eight. A summed number describes no purchase that actually happens.

One table per buying motion, labelled with its count ("Self-serve, 3 buying roles", "Purchased on behalf, 5 buying roles"). The header and the key finding state the counts per buying motion.

## What this is not

**Not copy.** The messaging framework gives every asset the same facts and the same words to build from. Headlines, pages and emails get written from it, not in it.

**Not the positioning.** Positioning decides the comparison. The messaging framework says it out loud, per buying role.

**Not a brand bible.** The biggest framework on the market runs to 35 sections, sold by a firm whose own site admits most frameworks die in implementation. The death rate is the design constraint: the sheet is one page, and everything that will not fit was not going to be used anyway.

## The known failure

Messaging documents die on drives. Practitioners agree on why: marketing builds them without sales, they ship as reference documents instead of talk tracks, they have too many components, and nobody reinforces them.

Design against it from the start:

- **One page.** Not a deck, not a wiki.
- **Messages short enough to say on a call from memory.** That is the talk-track test.
- **The primary persona marked**, so nobody guesses which message the homepage uses.
- **Exported to where the team works**, and as an AI context file.

## The messaging hierarchy

| | |
|---|---|
| **Vision** | One sentence. Why the company exists. Changes rarely |
| **Elevator pitch** | Two sentences a stranger could repeat |
| **Positioning statement** | Taken from the Positioning output. Never rewritten here. Internal only |
| **Message pillars** | Exactly three. Every message hangs from them |

**Exactly three pillars.** Each must be distinct (not the same thing said three ways), durable (holds for six to twelve months), and differentiated. The test for differentiated is the **competitor swap test**: place the pillar on a competitor's homepage. If it describes their product accurately, it fails. Run it against the competitors in The Fifty, using their homepage text read in full and dated, and show the result per competitor. When a pillar fails, suggest a replacement drawn from evidence (a differentiator candidate from the Table-stakes read, a gap from the Buying committee).

## Message per buying role

One row per buying role from the Buying committee output, grouped by buying motion. Use the buying role names from that output (end user, economic buyer, champion, co-decision maker, influencer, incumbent owner, and so on), with a short description beside each ("partner or spouse", "colleague who uses a competitor").

Each row carries:

| | |
|---|---|
| **Buying role** | The role name, with a short description |
| **Key question** | From the Buying committee, at the buying stage where it matters most |
| **Message** | The answer, one or two sentences, sayable from memory |
| **Proof point** | The evidence behind the message, with its grade |

**The primary persona is marked**: the homepage message. It is the row the hero copy and the elevator pitch are written from. This is the buyer closest to the problem, explicitly not the economic buyer when that is a different person, who is too far from the problem to care. One message on the homepage, the rest on file for the pages, decks and emails that address each role.

**Where no message can honestly be written**, because an input does not exist (such as a price), say so in the row and name the output that fills it. Never draft copy to paper over a missing decision.

**The regulator gets no marketing message.** Note the rule it sets (a risk warning on every message, no promised returns) instead.

## Writing the messages

**Capability first.** Buyers do not care about abstract benefits, they care about what the product does. "Enhance operational efficiency and decision-making" is a message nobody remembers and everybody writes. The order that works:

1. **The capability** — what the buyer does with the product, as a verb phrase
2. **The feature** — the thing that powers it, named
3. **The benefit** — what changes, stated as the removal of the problem in their situation

A message may carry all three, but it opens with the capability.

**Buyers' words.** Every message is built from the language bank. If the buyer says "spreadsheet problem", the message says spreadsheet, not "manual process inefficiency". Where no quote exists for a buying role, the message is written plainly and its proof point is graded unknown, because the words are yours, not theirs.

**Banned:** jargon the buyer would not say, any word from the marketing pile (revolutionise, supercharge, seamless, unlock, empower, leverage), balanced two-part lines, and any sentence that would work on a poster.

## Proof point grades

Every message carries one, using the same grades as Positioning.

| Grade | Means | Drawn as |
|---|---|---|
| Proven | Evidence exists, it is yours, a stranger could check it | Solid, green in the app |
| Borrowed | True, but the evidence is a benchmark, another market, or incomplete | Half |
| Unknown | Nobody has checked | Dashed outline |
| Contradicted | Your own site or data disagrees | Outlined, struck through |

In the sheet, the grade is a plain word in the proof point column. In the report, it is drawn. A framework that is mostly unknown is the honest early-stage result, and it doubles as the Claim check's queue.

## The two tests

Run both before shipping, and show the results:

**The competitor swap test.** Each pillar against each named competitor. Passes or fails per competitor, drawn, with one plain sentence explaining the test.

**The talk-track test.** Each message read aloud once, then said from memory. In the app: a word count (flag anything over 25 words), a play button, and a tick when the user can say it without reading. A message that cannot survive that is too long, and a message that embarrasses the person saying it is wrong. Rewrite or cut.

## Hand-offs

The primary persona message becomes the homepage headline (Landing page review). The other rows become their pages, deck slides and battlecards (Sales enablement). Missing inputs go to the output that fills them (Packaging and pricing for fees). Unknown proof points become the Claim check's queue. The sheet becomes the baseline Message drift checks the live site against. If none of that happens, the framework died on a drive like the rest.

## The report's structure

Header: `Messaging framework · <buying roles per buying motion, never summed> · <sources> · <date>`

**01 · Messaging hierarchy** — vision, elevator pitch, positioning statement, three message pillars, each pillar with its competitor swap test drawn and captioned.

**02 · Message per buying role** — grouped by buying motion, each group labelled with its own count. One row per buying role: role, key question, message, proof point with its grade. The primary persona marked. Opens with one sentence saying these are separate sales.

**03 · Language bank** — the exact buyer phrases the messages were built from, with counts.

**04 · Key finding** — one sentence. A fact with an action inside it, with counts stated per buying motion.

**05 · Limitations** — always names the buying roles with no direct quotes behind their messages.

Five sections.

## The sheet's structure

One tab or one page. Top block: vision, elevator pitch, positioning statement, the three message pillars. Then one table per buying motion, columns: buying role, key question, message, proof point grade as a plain word, primary persona flag. Nothing else, no charts, no findings, no notes. Plain formats only: Google Sheets, xlsx, Notion or Markdown, whatever the client's team actually opens, saved to their drive.

## Drawing rules (report)

- The message table is the centre of the document. Give it room.
- Grades in fill. Green only on proven proof points and passing swap-test cells.
- Swap-test results drawn per pillar against named competitors.
- Counts as marks where quotes are counted.
- The primary persona row visually marked with a green edge, not just labelled.

## Language

Standard product marketing terms on every label and heading. Never a label built from "who, what, which, where" phrasing. Messages themselves stay in buyers' words.

| Use | Instead of |
|---|---|
| Messaging framework, messaging sheet | Messaging matrix, the sheet |
| Messaging hierarchy: vision, elevator pitch, positioning statement, message pillars | The spine |
| Buying roles (end user, economic buyer, champion, co-decision maker, influencer, incumbent owner) | Seats, the people who have to say yes, the one who handles the money |
| Buying motion: self-serve, sales-led, partner, purchased on behalf, renewal | Routes, buying for themselves, bought by an employer |
| Key question | What they ask, pain point |
| Message | The line, talk track |
| Proof point, graded Proven, Borrowed, Unknown, Contradicted | The proof, proof states |
| Primary persona (homepage message) | The person the homepage talks to |
| Competitor swap test | Paste test |
| Talk-track test | Use test, says it from memory |
| Language bank | The words to use, from real users |
| AI context file | (new) |
| Key finding, Limitations | The finding, what can't be known |

## Voice

- Plain and direct. Their words in quotes, yours outside them.
- No slogans, no balanced two-part phrases, no line whose job is to sound clever. This rule is the product here, not just the style.
- The key finding is a fact, not a formulation.
- Sentence case. British spelling. No em dashes.

## Rules

- **Two deliverables: the messaging sheet and the report.** The sheet on real engagements always; the report alone only for demo and portfolio use.
- **Counts per buying motion, never summed.**
- **The rows come from the Buying committee output.** No buying committee work, no messaging framework.
- **Exactly three message pillars**, each distinct, durable and passing the competitor swap test.
- **One primary persona, marked.** All rows on file, one on the homepage.
- **Capability first, in buyers' words.** A message with no quote behind it has its proof graded unknown.
- **Every message carries a graded proof point.**
- **Every message passes the talk-track test** or gets rewritten.
- **A missing input gets named, not papered over with copy.**
- **One page.** What does not fit was not going to be used.
- **Never a percentage under thirty.**
- **Read the source, never the snippet.** Competitor homepage text used in the swap test comes from their pages read in full, dated.
- **Name organisations, never individuals**, when the work is confidential.
